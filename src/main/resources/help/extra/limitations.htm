Known limitations

Parser

  • Calls without parentheses whose first argument starts with ( (SetTimer () => stmt, 100) are not supported. Use ;@ignore-next-line or write the call with parentheses: SetTimer(() => stmt, 100).
  • Inside parentheses, a next line that starts with a fat arrow function (x := (a / () => 1)) is not recognized as a concatenation. (A next line starting with !, not, ~, ++ or {...} is an error in AutoHotkey as well.)
  • The command form of a method call (obj.Method "x", 1) is read as a concatenation; it works in AutoHotkey but has no parameter info. Prefer obj.Method("x", 1).
  • A property block with its accessor on the same line (Prop { get => 1 }) is accepted, although AutoHotkey reports an error there; write the accessor on its own line.
  • A command with an omitted first argument (Foo , x) is not supported.
  • Outside parentheses, a line only continues the previous one if it starts with and, or, is, in, contains, &&, ||, ??, ?, :, . (with a space after it) or ,. Other operators at the start of a line (=, :=, +, *, < …) are reported as an error, although AutoHotkey continues the previous line (if x / = 1); they could not be told apart from hotkeys such as =:: or +a::. Put the operator at the end of the previous line or enclose the expression in parentheses.
  • Line breaks inside [ ] and { } never continue an implicit concatenation; this is deliberate, so that a forgotten comma stays an error.
  • AutoHotkey v2.1 is an alpha, and so is its support in the plugin; its own limitations are listed in AutoHotkey v2.1 (alpha).

If validation shows that AutoHotkey accepts such code, the errors are marked as "Syntax error (AutoHotkey accepts this code)".

Names and types

  • Variables are not resolved; navigation, completion and parameter info work with names only. Type declarations narrow member lists, but the plugin does not infer types from assignments.
  • Only the file itself and its directly included files are searched; Find Usages searches the reverse direction (the files that include the file of the definition); there is no project-wide search. Rename works on names, not types: check its preview (see below).
  • Files outside the project and outside the AutoHotkey library folders only get basic colors (see Navigation).

Rename: check the preview

Renaming a method safely requires knowing which class every call refers to. In AutoHotkey this is only decided when the script runs: the same call can reach methods of unrelated classes that merely share a name. The plugin therefore renames by name and always shows a preview first (Rename), in which you exclude the occurrences that belong to something else.

Which f does obj.f() call?

class X {
    f() {
        MsgBox "X.f"
    }
}

class Y {
    f() {
        MsgBox "Y.f"
    }
}

CallF(obj) {
    obj.f()          ; X.f or Y.f, depending on the argument
}

xobj := X(), yobj := Y()
CallF(xobj)
CallF(yobj)

Renaming X.f lists obj.f() in CallF in the preview, because the name matches. Whether it may be renamed depends on the objects passed to CallF: with a Y the call would break, so Y.f would have to be renamed as well, or the call stays. Go to declaration on f lists all candidates instead of guessing.

What no search can see:

  • dynamic names such as obj.%name%(), and names in strings that are used as names: HasMethod(obj, "f"), ObjBindMethod(obj, "f"), HasProp(obj, "count") (with Search in comments and strings they appear in the preview as text occurrences);
  • scripts outside the project, and scripts that are not connected to the definition's file by #Include.

After renaming, validate the main script: a call of a function that no longer exists is a load error in AutoHotkey v2 and shows up at once. Calls of methods are only checked when they run.

Tip: unique names make renaming easy

If you consistently give methods, properties, functions and classes names that are unique in your project, every occurrence in the preview belongs to the renamed definition, and the preview is quick to check. The same holds for the IDE's Replace in Files (Edit > Find > Replace in Files, Ctrl+Shift+R), for example to rename a variable:

  • turn on Words, so that Count does not match CountItems;
  • leave Match case off, because AutoHotkey ignores case (obj.Count and obj.count are the same);
  • check the preview before replacing: occurrences in strings and comments are found as well.

In the example above, distinct names such as X.ShowGreeting and Y.ShowFarewell make every call unambiguous. When both classes have to share an interface on purpose, the shared name stays and is renamed in all classes together.

Running, validation, debugger

  • Running, validating, compiling and debugging need Windows and an installed AutoHotkey v2.
  • Runtime errors are shown by AutoHotkey in its own dialog, not in the console.
  • The debugger evaluates only variable and member paths, no expressions (see Debugger).
  • The popup help shows the pages of AutoHotkey v2.0.31 (v2.1 files: v2.1-alpha.39), the external help those of the installed version (see Versions).
