Deploying tools and setting versions

Tools you use every day should not run from the project folder: every compilation there would replace the version you rely on. Two actions help:

  • Deploy to Local Target... copies the tool to a fixed place (for example C:\bin), optionally after compiling it.
  • Set Version... sets the version of the tool in its scripts, commits the project and sets a Git tag.

The two are independent: you decide when a version is worth a number and when it is deployed. Both first save all modified files, also settings.ahk-plugin.ini, so that Deploy reads and Set Version commits what you see in the editor. Both are in the Code menu and in the context menus of the editor and the Project view.

They follow one rule: one tool = one project. A tool may consist of several scripts and executables, for example a GUI and a console variant, but it is one unit with one version, deployed together. So both actions always work on the whole project, whatever file is open, and their menu entries name it (Deploy 'MyTool' to Local Target...). They appear in every project that contains an AutoHotkey file or a settings.ahk-plugin.ini; no file has to be open. Tools that have nothing in common but the language get a project each; the overhead of a project is small.

settings.ahk-plugin.ini

The settings of Deploy are in the file settings.ahk-plugin.ini in the project root; Set Version only reads its section [SetVersion] and also works without the file:

[Install]
Destination=C:\bin
Message=Close the running tool first.`nThen press Deploy.
RequiresAdmin=false
GenerateOverview=true
CompileBeforeInstall=true

[Overwrite]
mytool.exe=.
console\mytool-console.exe=.
pictures\*.png=pictures

[KeepExisting]
mytool.ini=%APPDATA%\mytool\

[SetVersion]
scratch\=exclude

Create Settings... (in the same menus, as long as the project root has no such file) writes a documented default settings.ahk-plugin.ini into the project root and opens it: every option is explained in comments and commented out, so the defaults apply until you remove a ;. A commented-out switch shows the value that changes its default (usually true), so removing the ; is all it takes. Examples use the name of the project. Deploy to Local Target... offers the same when the file is missing.

Comments are lines starting with ; (spaces before it are allowed); a ; later in a line is part of the value. Section and key names are case-insensitive. Keys and values may be enclosed in double quotes, which are removed; spaces inside a file name are kept (my console\my console.exe=.), only = cannot be part of it. Every key, and every source in a section, may appear only once. Unknown sections and keys are errors. A mistake of the file itself (unknown section, a line without =, a line twice) stops every action; a mistake in a section only stops the action that uses it ([Install], [Overwrite] and [KeepExisting]: Deploy; [SetVersion]: Set Version).

[Install]

KeyMeaning
DestinationAbsolute folder for relative targets, usable as %DESTINATION% (it wins over an environment variable of that name). May be omitted; then all targets must be absolute.
MessageText shown in the confirmation, for example "close the running tool first". `n is a line break; %DESTINATION% and environment variables are resolved, %% is a percent sign.
RequiresAdmintrue: all files are copied by one elevated process (one UAC prompt); the confirmation then always shows a prominent notice. The plugin does not find out by itself whether administrator rights are needed; without them copying into a protected folder fails with an error.
GenerateOverviewShow an overview in the confirmation (default true): the destination, "compile mytool.ahk" for each script to compile, and the lines of [Overwrite] and [KeepExisting] as written, without comments.
CompileBeforeInstallCompile what is copied (default true): see Compiling before copying.

Missing switches are false, except GenerateOverview and CompileBeforeInstall.

[Overwrite] and [KeepExisting]

Each line is source=target. [Overwrite] replaces existing files; [KeepExisting] only copies if the target does not exist yet (for configuration files the user may have changed) and reports the others as skipped.

  • Source: a file relative to the project root, never outside of it (.. and absolute paths are not allowed). The wildcards * and ? are allowed in the file name, not in folder names; they are not recursive and match only files. A missing file or a wildcard without a match is an error, except for the executables that the compilation creates.
  • Target: absolute, or relative to Destination. Environment variables of the IDE (%APPDATA%) and %DESTINATION% are resolved. The target is a folder if it ends with \, /, . or .., if it is Destination itself (. or %DESTINATION%, also before it exists), or if it already exists as a folder; the file keeps its name. Otherwise it is the new file name. With a wildcard in the source the target is always a folder. Missing folders are created.
  • Several targets for one file: a source may appear only once per section; use wildcards to name it again: tool.exe=dest1, tool.ex?=dest2, tool.e?e=dest3.

Compiling before copying

By default (CompileBeforeInstall=true) the plugin compiles what is copied, and only that. Every source of [Overwrite] and [KeepExisting] that names an executable (.exe, without wildcards) and has a script of the same name next to it is compiled from that script with Ahk2Exe before anything is copied, like Compile with Ahk2Exe:

  • mytool.exe is compiled from mytool.ahk, console\mytool-console.exe from console\mytool-console.ahk. Each script is compiled once, in the order of the lines, every time (there is no check whether an executable is up to date).
  • Such a script needs a line ;@Ahk2Exe-Base, and a line ;@Ahk2Exe-ExeName in it must not name another file. Otherwise the deployment stops before anything happens: add the line to the script, or remove the executable from the settings.
  • An executable without a script of the same name is just copied; it must exist. Lines with wildcards (*.exe) are never compiled.
  • A compilation error stops the deployment before anything is copied.

With CompileBeforeInstall=false nothing is compiled and the executables are copied as they are; the confirmation warns if an executable is older than the scripts next to it.

Deploy to Local Target

Deploy to Local Target... needs settings.ahk-plugin.ini in the project root with at least one line in [Overwrite] or [KeepExisting]. The plugin then

  1. reads the file and checks everything: sources, targets, variables, the scripts to compile. Any problem is shown at once and nothing happens;
  2. always asks for confirmation (with the notice about administrator rights, the message, the overview and warnings; see below);
  3. compiles (unless CompileBeforeInstall=false) and copies, in this order;
  4. shows a report in the Run tool window: what was compiled, copied and skipped. At the first failure the remaining steps are stopped; nothing is rolled back.

The confirmation warns if an executable is older than the scripts next to it (with CompileBeforeInstall=false), and if the project has uncommitted changes. Deploying never commits or tags anything.

Copying writes the content into the target: a new file gets the permissions of its folder, an overwritten file keeps its own. The modification time of the source is kept. Environment variables are always resolved in the IDE, also with RequiresAdmin=true, so %APPDATA% is your folder even if the elevated process runs as another administrator.

There is no step to stop a running tool or to run a program before or after the deployment; use Message to remind yourself.

A tool with several programs

A tool may consist of scripts that are deployed as they are and of programs that are compiled. Example: a script started by the Windows Task Scheduler (easy to change and restart) and two compiled variants of the tool, one with a GUI and one for the console:

MyTool\                        ; the project root
  settings.ahk-plugin.ini
  watch.ahk                    ; ;@Ahk2Exe-SetVersion 1.4.0 (not compiled)
  mytool.ahk                   ; ;@Ahk2Exe-Base ..., ;@Ahk2Exe-SetVersion 1.4.0
  console\mytool-console.ahk   ; ;@Ahk2Exe-Base ..., ;@Ahk2Exe-SetVersion 1.4.0
  lib\shared.ahk               ; included by both variants
[Install]
Destination=C:\bin\mytool
CompileBeforeInstall=true

[Overwrite]
watch.ahk=.
mytool.exe=.
console\mytool-console.exe=.
  • Deploy compiles both variants and copies everything, whatever file is open.
  • Versions: all three scripts carry the line ;@Ahk2Exe-SetVersion; Set Version... changes all of them at once, also in watch.ahk, which is not compiled. lib\shared.ahk needs no line.
  • Validate and Compile use the script of the selected AutoHotkey run configuration, from whatever file is open. To test both variants independently, create a run configuration for each and select the one you work on; without a run configuration they use the current file.

Uncommitted changes

The confirmation shows "The project has uncommitted changes" when Git reports changes in the project. The deployed version then does not match any commit: you cannot find out later which code it was built from, and a version tag points to a commit without these changes. Commit first (or use Set Version) if the deployed version should be reproducible.

Set Version

The version lives in the scripts, in the compiler directive that sets the file and product version of the executable:

;@Ahk2Exe-SetVersion 1.0.2

Set Version... reads this line in every AutoHotkey file of the project (excluded folders are skipped; files without the line are left alone) and shows a dialog:

  • the current version and the scripts that get the new one. If the scripts have different versions, the dialog says so; the highest counts as the current one, and all get the new version;
  • the next patch, minor or major version (1.0.2 becomes 1.0.3, 1.1.0 or 2.0.0; a text after the numbers such as -beta and a leading v are dropped), or any other version (without a leading v, which is unusual for Windows versions, and without spaces, commas, %, ; and `);
  • Commit the project and create tag v<version>: commits all changes of the project together with the new version and sets an annotated tag on that commit, so the tag marks exactly the sources of the deployed tool. Staged changes outside the project stay staged. An existing tag is refused: choose another version;
  • the message of commit and tag, proposed as "Release MyTool v1.0.3".

Commit and tag are only possible if every file of the project is either versioned or ignored (.gitignore): a new file nobody added yet would be missing in the tagged state. Otherwise the check box is disabled and the dialog names these files; add them to Git or to .gitignore and set the version again. Uncommitted changes of versioned files are listed in the dialog and committed together with the version. Without Git, or if the project is not in a repository, the check box is disabled as well. Without the check box only the lines are changed.

Scripts that should keep their own version line, such as experiments or old variants, are listed in the section [SetVersion] of settings.ahk-plugin.ini:

[SetVersion]
scratch\=exclude
old\mytool-v1.ahk=exclude
test\*.ahk=exclude

Each line is path=exclude. The path is relative to the project root and names files like a source of [Overwrite] (* and ? only in the last name, no ..); ending with \ it names a folder with everything below it, as in .gitignore (but always from the project root). test\*.ahk only names the files directly in test. Excluded scripts are left out silently. They still count for commit and tag: to keep files out of Git, list them in .gitignore.

The plugin then changes the lines in the editor (one Undo takes them all back), saves the files, commits and tags, and reports the result in a notification.

The line is read as Ahk2Exe reads it: ;@Ahk2Exe-SetVersion in any case at the start of the line (spaces before it allowed), then the version; a comment after spaces (;@Ahk2Exe-SetVersion 1.0.2 ; comment) is not part of it. Lines in block comments /* */ and between ;@Ahk2Exe-IgnoreBegin and ;@Ahk2Exe-IgnoreEnd do not count. A script may have only one such line, with the version written out (a version computed with %...% cannot be changed). Ahk2Exe turns a text such as 1.0.2-dev into the binary version 1.0.2.0.

Code shared by several tools usually lies in a library folder outside the project; a deployed .exe contains the library as it was when it was compiled, a deployed .ahk uses the current library.
