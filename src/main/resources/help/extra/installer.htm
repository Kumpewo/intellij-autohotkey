Deploying tools and setting versions

Tools you use every day should not run from the project folder: every compilation there would replace the version you rely on. Two actions help:

  • Deploy to Local Target... copies the tool to a fixed place (for example C:\bin), optionally after compiling it.
  • Set Version... sets the version of the tool in its scripts, commits the project and sets a Git tag.

The two are independent: you decide when a version is worth a number and when it is deployed. Both first save all modified files, also settings.ahk-v2-plugin.ini, so that Deploy reads and Set Version commits what you see in the editor. Both are in the Code menu and in the context menus of the editor and the Project view.

They follow one rule: one tool = one project. A tool may consist of several scripts and executables, for example a GUI and a console variant, but it is one unit with one version, deployed together. So both actions always work on the whole project, whatever file is open, and their menu entries name it (Deploy 'MyTool' to Local Target...). They appear in every project, also in one without AutoHotkey files: deploying and setting versions work for tools in any language. Tools that have nothing in common but the language get a project each; the overhead of a project is small.

settings.ahk-v2-plugin.ini

The settings of Deploy are in the file settings.ahk-v2-plugin.ini in the project root; Set Version only reads its section [SetVersion] and also works without the file:

[Deploy]
Destination=C:\bin
Message=Close the running tool first.`nThen press Deploy.
GenerateOverview=yes
RequiresAdmin=no
Compile=yes
EmbedOrigin=yes

[Install]
mytool.exe=.
console\mytool-console.exe=.
pictures\*.png=pictures

[InstallIfMissing]
mytool.ini=%A_AppData%\mytool\

[Cleanup]
old-name.exe=.

[SetVersion]
scratch\=no

Create Settings... (in the same menus, as long as the project root has no such file) writes a documented default settings.ahk-v2-plugin.ini into the project root and opens it: every option is explained in comments and commented out, so the defaults apply until you remove a ;; only [SetVersion] leaves the folders scratch\ and test\ out from the start. A commented-out switch shows the value that changes its default (usually yes), so removing the ; is all it takes. Examples use the name of the project and the files in the project root (;notes.md=., ;*.md=yes; without such files ;MyTool.cmd=.). In a folder below the library projects folder the file is that of a library project instead: Destination is the user library folder, and every AutoHotkey file in the project root is listed in [Install] with the target {set target}, which you replace before the first deployment. Deploy to Local Target... offers the same when the file is missing.

Explanations start with ;; in the first column and a space; commented-out options start with a single ;. The bar above the file switches between a short and an explained file; each link is one undo step:

  • Remove Explanations and Compact removes all lines starting with ;; and a space (also your own) and the empty lines inside the sections. Commented-out options and other comments stay.
  • Restore Explanations inserts the current explanations. It also adds sections, options and general examples you have deleted, always commented out, so the meaning of the file never changes. An active option gets no examples.

For comments of your own, use a single ; with a space, or ;;;; in [Deploy] they stay above the option that follows them. Ctrl+Q shows the explanation of the option or section at the caret, also in the short file. A setting decides which form new files have.

Comments are lines starting with ; (spaces before it are allowed); a ; later in a line is part of the value. Section and key names are case-insensitive. Keys and values may be enclosed in double quotes, which are removed; spaces inside a file name are kept (my console\my console.exe=.), only = cannot be part of it. Every key, and every source in a section, may appear only once (except in [Cleanup]). Unknown sections and keys are errors. A mistake of the file itself (unknown section, a line without =, a line twice) stops every action; a mistake in a section only stops the action that uses it ([Deploy], [Install], [InstallIfMissing], [AddBanner] and [Cleanup]: Deploy; [SetVersion]: Set Version).

Variables in Destination, targets, Message and Banner=file: are written in percent signs: the folder variables of AutoHotkey, found like AutoHotkey finds them (also a "Documents" folder that Windows redirects): %A_MyDocuments%, %A_AppData%, %A_AppDataCommon%, %A_Desktop%, %A_DesktopCommon%, %A_ProgramFiles%, %A_Programs%, %A_ProgramsCommon%, %A_StartMenu%, %A_StartMenuCommon%, %A_Startup%, %A_StartupCommon%, %A_Temp%, %A_UserName%, %A_ComputerName%, %A_WinDir%; %LIBRARY_PROJECTS% (the setting Library projects folder); in targets and Message also %DESTINATION%. %% is a percent sign. Environment variables such as %USERPROFILE% are not resolved; an unknown name is an error.

Settings of plugin version 2.1 were in settings.ahk-plugin.ini, with other names: [Install] for the options (now [Deploy]), [Overwrite] (now [Install]), [KeepExisting] (now [InstallIfMissing]), [ApplyCopyNotice] (now [AddBanner]), CopyNotice (now Banner) and CompileBeforeInstall (now Compile). This version still reads such a file if the project has no settings.ahk-v2-plugin.ini. The confirmation of Deploy then shows a gray hint and the button Update Settings: it turns the old file into settings.ahk-v2-plugin.ini with the new names, also in its comments (Git sees a rename), and shows the confirmation again. If both files exist, the new one counts and the confirmation warns about the old one. Plugin version 2.5.0 will no longer read the old file. Old names in the new file are errors that name the new name.

[Install] and [InstallIfMissing]

Each line is source=target. [Install] replaces existing files; [InstallIfMissing] only copies if the target does not exist yet (for configuration files the user may have changed) and reports the others as skipped.

The copies of [Install] are made read-only in the file system, as a reminder to edit the source instead (where the drive does not allow it, for example some network drives, the copy simply stays writable). The next deployment overwrites them without asking. Copies of [InstallIfMissing] stay writable, as the user may change them.

  • Source: a file path that always starts at the project root (also without a leading \), never outside of it (.. and absolute paths are not allowed). The wildcards * and ? are allowed in the file name, not in folder names; they are not recursive and match only files. A missing file or a wildcard without a match is an error, except for the executables that the compilation creates.
  • Target: absolute, or relative to Destination. Variables such as %A_AppData% and %DESTINATION% are resolved. The target is a folder if it ends with \, /, . or .., if it is Destination itself (. or %DESTINATION%, also before it exists), or if it already exists as a folder; the file keeps its name. Otherwise it is the new file name. With a wildcard in the source the target is always a folder. Missing folders are created.
  • Several targets for one file: a source may appear only once per section; use wildcards to name it again: tool.exe=dest1, tool.ex?=dest2, tool.e?e=dest3.
  • One target, one line: two lines must not give the same target, also not one in [Install] and one in [InstallIfMissing]; the deployment stops with an error, so you decide which one you mean.

[Cleanup]

Removes leftovers of earlier deployments, for example the old file after a tool was renamed. Each line is files=folder:

  • Folder (after the =): absolute, or relative to Destination, with variables as in targets. It is always a folder; a file there is an error.
  • Files (before the =): relative to that folder, with the wildcards * and ? in the file name. Only files are removed, not folders, and not in subfolders.
  • Examples: pictures\*.png=. removes <Destination>\pictures\*.png; test.exe=C:\bin removes C:\bin\test.exe.
  • A folder that does not exist, or files without a match, remove nothing. A file that the same deployment writes is an error. The same files may be named for several folders.

This is a risky step, so it always asks: if there is something to remove, a second dialog after the confirmation lists every file with its full path, with three buttons: Remove and Deploy, Deploy Without Removing and Cancel (the default). The files are moved to the Recycle Bin before copying, with RequiresAdmin=yes by the same elevated process. They are never deleted for good: on a drive without a Recycle Bin (a network or removable drive) the deployment stops with an error. The report names every removed file.

Renaming files of the project

Renaming or moving a file or folder of the project in the IDE (Rename, Move, drag and drop in the Project view) also updates settings.ahk-v2-plugin.ini: the sources of [Install] and [InstallIfMissing] that name it (for a script also the executable of the same name next to it, Gui.exe for Gui.ahk), and the selectors of [SetVersion] and [AddBanner] that name exactly this file or folder (no wildcards).

  • The file name changes and the file is deployed to a folder (Gui.ahk=v2\) or under its old name: a dialog asks what happens to the deployed file.
    • Keep Target Name (the default): Gui-v2.ahk=v2\Gui.ahk. Scripts that use the deployed file (#Include <Gui>) keep working.
    • Rename Target Too: Gui-v2.ahk=v2\, and a line Gui.ahk=v2\ in [Cleanup] removes the old copy at the next deployment (not for [InstallIfMissing], whose files belong to the user).
    • Edit Myself: only the source changes, and the file opens at the target.
    • Cancel: nothing changes.
  • Other changes (moving, a renamed folder, a target with another name) are made at once, and a dialog shows them; Edit Myself opens the file. Undo in its editor reverts the change.
  • A line of [Cleanup] that would remove a new target is removed. If the script names its executable with ;@Ahk2Exe-ExeName, the dialog reminds you to adjust that line.

Not every change can be followed. Renaming or moving in Windows Explorer or another program is not noticed, and lines with wildcards (*.ahk=v2\) stay as they are, so their targets take the new name. After such changes, and whenever a deployment does something unexpected, check settings.ahk-v2-plugin.ini carefully: the overview in the confirmation of Deploy shows what will be copied where.

Selectors and values of [AddBanner] and [SetVersion]

Both sections have lines selector=value. The selector is written like a line of .gitignore, relative to the project root:

  • Without a separator (except at the end) it applies in every folder: *.ahk, test.ahk. With one at the start or in the middle it starts at the project root: /x.ahk, lib/*.ahk. / and \ are both separators.
  • A separator at the end names a folder with everything below it: scratch\ (every folder of that name), /scratch\ (only the one in the root).
  • * matches any characters except a separator, ? one, [a-z] one of a range; ** any number of folders: **/gen/*.js, docs/**. Case does not matter.
  • If several lines match, the last one wins, as in .gitignore: write exceptions below the general line (*.md=yes, then drafts\=no).

yesThe files are included, with the comment of their type (see Known comment styles), e.g. ; for .ahk, # for .py, // for .js. For a type the plugin does not know, yes is an error; then the value must name the comment.
noThe files are left alone.
line:<start> [<end>]Included; every comment line is <start> text <end>: line:REM, line:#, line:<!-- -->.
block:<start> <end>Included; one block comment: block:/* */.

Binary files (.exe, .dll, .png, .jpg, .jpeg, .gif, .bmp, .ico, .zip, .pdf, .chm) are never changed; a line that includes them only gives a warning.

Banner

A copy can say where its source is, so that nobody changes it by mistake, also outside the IDE. Banner in [Deploy] is the text; it is written as comments at the start of the copies:

[Deploy]
Destination=%A_MyDocuments%\AutoHotkey\Lib\
Banner=Installed copy of {source-relative} {version}, do not modify.`nEdit the source in project {project-name} and deploy.

[Install]
*.ahk=.
setup.cmd=.
readme.txt=.

[AddBanner]
test.ahk=no
setup.cmd=yes
readme.txt=line:#
  • Which files: every AutoHotkey file that [Install] copies, unless a line of [AddBanner] excludes it; other files only if a line includes them. Files of [InstallIfMissing] never get a banner, because the copy belongs to the user from then on (a banner saying "do not modify" would be wrong, and its version would never be updated); a line that includes one gives a gray hint. Without Banner nothing gets a banner.
  • Warnings: the confirmation tells you when the banner and the files do not fit together. With Banner but no file that gets it, it warns if a file could take a banner (for example run.cmd without a line *.cmd=yes); exclude such files with no to deploy them without a banner. If none of the deployed file types can take a banner (only .exe, .txt ...), a gray hint says so. Without Banner, it warns about a line that includes a deployed file, and about AutoHotkey files that would get a banner: set Banner, or write *.ahk=no in [AddBanner] if the tool is meant to be deployed without one.
  • Text: the value itself (`n starts a new line), a built-in template (@standard or @library, see below), file:<path>: the lines of a text file (UTF-8), relative to the project root, with variables, or find:<name>: the text file of that name in the project root or the nearest folder above it, for example Banner=find:banner.txt with one banner.txt in the folder that holds your projects. With find: you can move a project or reorganize the folders without changing its settings; a banner.txt deeper down (for example in the library projects folder) wins for the projects below it. If no folder contains the file, the deployment stops with a message: create the file, or switch to a built-in template. {project-name} is the folder name of the project, {project-path} its full path, {source-name} the file name of the source, {source-relative} its path relative to the project root (src\Gui.ahk), {source-path} its full path, {version} the version of its version line, {commit} the short Git commit of the project (with + if the source has uncommitted changes), {timestamp} the time of the deployment (2026-11-20 14:30), {computer} the name of this computer and {include} the line that includes a copy in a Lib folder (#Include <v2\Gui>). A line whose placeholders are all empty is left out: without a version line, without Git, or for a copy outside the Lib folders.
  • Templates: @library looks like this; its lines are as long as those of the head of Ahk2Exe directives, and the values are aligned four spaces after the longest label. @standard, for every other copy (a tool, a configuration ...), starts with INSTALLED ARTIFACT -- Do not modify here. Edit the source and deploy again. and has no line Use. 
    ; ---------------------------------------------------------------------------
; INSTALLED LIBRARY  -  Do not modify here. Edit the source and deploy again.
;
; Project     Gui [D:\Projects\Gui]
; Source      Gui.ahk
; Version     1.2.0
; Commit      a1b2c3d+
; Deployed    2026-11-20 14:30 on MYCOMPUTER
; Use         #Include <v2\Gui>
; ---------------------------------------------------------------------------
  • Comment: every line is a comment line in the first column (; text); with block: the start comes before the first line and the end after the last one. To put the start or the end on a line of its own, begin or end the text with `n.
  • Placement: the banner comes first in the copy, after a first line <?xml ...?>, #!..., the header of a registry file or @echo off; the rest of the file is copied unchanged (except for ;@Ahk2Exe-SetVersion in scripts that are not compiled). Only if the text uses {version}, the copy loses its own version line (;@SetVersion, # @SetVersion ...), because the banner shows the version already; a script with ;@Ahk2Exe-Base keeps it. The source in the project is never changed.
  • Encoding: a file with a byte order mark (UTF-8 or UTF-16) gets the text in its encoding. Any other file gets plain ASCII: every other character becomes _. The line break is the one of the first line of the file.
  • Line numbers: the banner moves the lines of the copy down. An error message of a script that runs from the copy names the line of the copy; Open Library Project takes the banner into account.

Compiling before copying

By default (Compile=yes) the plugin compiles what is copied, and only that. Every source of [Install] and [InstallIfMissing] that names an executable (.exe, without wildcards) and has a script of the same name next to it is compiled from that script with Ahk2Exe before anything is copied, like Compile with Ahk2Exe:

  • mytool.exe is compiled from mytool.ahk, console\mytool-console.exe from console\mytool-console.ahk. Each script is compiled once, in the order of the lines, every time (there is no check whether an executable is up to date).
  • Such a script needs a line ;@Ahk2Exe-Base, and a line ;@Ahk2Exe-ExeName in it must not name another file. Otherwise the deployment stops before anything happens: add the line to the script, or remove the executable from the settings.
  • An executable without a script of the same name is just copied; it must exist. Lines with wildcards (*.exe) are never compiled.
  • A compilation error stops the deployment before anything is copied.

With Compile=no nothing is compiled and the executables are copied as they are; the confirmation warns if an executable is older than the scripts next to it.

Where a copy comes from

By default (EmbedOrigin=yes) the copies lead back to their project:

  • The built-in banners @standard and @library name the project folder and the computer on which you deployed.
  • An executable of [Install] with a script of the same name next to it gets the same as text at its end, with or without Compile. The program itself and its version information stay as they are, and the executable in the project is not changed: 
    [ahk-v2-plugin]
ProjectPath=C:\Projects\MyTool
ProjectComputer=MYCOMPUTER
    A tool of your own can read the end of the file (UTF-8, the last [ahk-v2-plugin] counts) to open the project. Other executables and the files of [InstallIfMissing] are copied unchanged, and so is a signed executable, whose signature would become invalid (a gray hint says so).

Privacy: the project folder (often with your user name) and the computer name are readable for everyone who gets such a copy. If you pass deployed files on, set EmbedOrigin=no: then the built-in banners name only the project, and nothing is added to executables. Your own banner texts and files are not affected; there the placeholders decide.

Optional extra: OpenInIDE, a separate project, adds an entry to the context menu of the Windows Explorer that opens the project of such a copy in IntelliJ IDEA. It reads the built-in banners and the text at the end of an executable, not your own banner texts, and supports no other IDE. You compile it yourself.

Deploy to Local Target

Deploy to Local Target... needs settings.ahk-v2-plugin.ini in the project root with at least one line in [Install] or [InstallIfMissing]. The plugin then

  1. reads the file and checks everything: sources, targets, variables, the scripts to compile. Any problem is shown at once and nothing happens;
  2. always asks for confirmation (with the notice about administrator rights, the message, the overview and warnings; see below);
  3. if [Cleanup] finds files, asks a second time and lists each of them;
  4. compiles (unless Compile=no), moves the files of [Cleanup] to the Recycle Bin (if confirmed) and copies, in this order;
  5. shows a report in the Run tool window: what was compiled, copied and skipped. At the first failure the remaining steps are stopped; nothing is rolled back.

The confirmation warns if an executable is older than the scripts next to it (with Compile=no), if the banner and the files do not fit together, and if the project has uncommitted changes. Deploying never commits or tags anything.

Copying writes the content into the target: a new file gets the permissions of its folder, an overwritten file keeps its own. The modification time of the source is kept. Variables are always resolved in the IDE, also with RequiresAdmin=yes, so %A_AppData% is your folder even if the elevated process runs as another administrator.

There is no step to stop a running tool or to run a program before or after the deployment; use Message to remind yourself.

A tool with several programs

A tool may consist of scripts that are deployed as they are and of programs that are compiled. Example: a script started by the Windows Task Scheduler (easy to change and restart) and two compiled variants of the tool, one with a GUI and one for the console:

MyTool\                        ; the project root
  settings.ahk-v2-plugin.ini
  watch.ahk                    ; ;@SetVersion 1.4.0 (not compiled)
  mytool.ahk                   ; ;@Ahk2Exe-Base ..., ;@Ahk2Exe-SetVersion 1.4.0
  console\mytool-console.ahk   ; ;@Ahk2Exe-Base ..., ;@Ahk2Exe-SetVersion 1.4.0
  lib\shared.ahk               ; included by both variants
[Deploy]
Destination=C:\bin\mytool
Compile=yes

[Install]
watch.ahk=.
mytool.exe=.
console\mytool-console.exe=.
  • Deploy compiles both variants and copies everything, whatever file is open.
  • Versions: all three scripts carry a version line; Set Version... changes all of them at once, also in watch.ahk, which is not compiled. lib\shared.ahk gets a line ;@SetVersion as well; a line lib\=no in [SetVersion] leaves it alone.
  • Validate and Compile use the script of the selected AutoHotkey run configuration, from whatever file is open. To test both variants independently, create a run configuration for each and select the one you work on; without a run configuration they use the current file.

Uncommitted changes

The confirmation shows "The project has uncommitted changes" when Git reports changes in the project. The deployed version then does not match any commit: you cannot find out later which code it was built from, and a version tag points to a commit without these changes. Commit first (or use Set Version) if the deployed version should be reproducible.

Set Version

The version lives in the scripts. A script to be compiled (with a line ;@Ahk2Exe-Base) has it in the compiler directive that sets the file and product version of the executable, every other AutoHotkey file in a comment:

;@Ahk2Exe-SetVersion 1.0.2     ; with ;@Ahk2Exe-Base
;@SetVersion 1.0.2             ; without

The reason for the comment: Ahk2Exe also obeys the directives of included files, and the last version wins. With ;@Ahk2Exe-SetVersion in a library, your program would get the version of the library. Set Version turns such a line into ;@SetVersion (and the other way round if the script has ;@Ahk2Exe-Base), and Deploy does the same in the copies of [Install]: for libraries from earlier versions of the plugin it is enough to deploy them again.

Set Version... sets this line in every AutoHotkey file (.ahk, .ah2, .ahk2) of the project, deployed or not; a file without the line gets one (see [SetVersion] to leave files out or to include other files). It shows a dialog:

  • the current version and the scripts that get the new one. If the scripts have different versions, the dialog says so; the highest counts as the current one, and all get the new version;
  • the next patch, minor or major version (1.0.2 becomes 1.0.3, 1.1.0 or 2.0.0; a text after the numbers such as -beta and a leading v are dropped; without any version yet 0.0.1, 0.1.0 or 1.0.0), or any other version (without a leading v, which is unusual for Windows versions, and without spaces, commas, %, ; and `). The field always shows the chosen version, so you can start from it: choose Minor, then add -beta in the field;
  • Commit the project and create tag v<version>: commits all changes of the project together with the new version and sets an annotated tag on that commit, so the tag marks exactly the sources of the deployed tool. Staged changes outside the project stay staged. An existing tag is refused: choose another version;
  • the message of commit and tag, proposed as "Release MyTool v1.0.3". It may have several lines; Ctrl+Enter sets the version.

Long lists of files are shortened; the tooltip shows more of them. This dialog and the confirmation of Deploy remember their size.

Commit and tag are only possible if every file of the project is either versioned or ignored (.gitignore): a new file nobody added yet would be missing in the tagged state. Otherwise the check box is disabled and the dialog names these files; add them to Git or to .gitignore and set the version again. Uncommitted changes of versioned files are listed in the dialog and committed together with the version. Without Git, or if the project is not in a repository, the check box is disabled as well. Without the check box only the lines are changed.

The section [SetVersion] of settings.ahk-v2-plugin.ini changes which files get the version, with the selectors and values of [AddBanner]:

[SetVersion]
scratch\=no
/old\mytool-v1.ahk=no
readme.md=yes
version.txt=line:#
  • Excluded files keep their own version line, for example experiments or old variants. They still count for commit and tag: to keep files out of Git, list them in .gitignore.
  • Included files of other types get the version as well. A file without a version line gets one: ;@SetVersion 1.0.3 (or the directive) in an AutoHotkey file, below its #Requires line (without one, as the first line); @SetVersion 1.0.3 in the comment of any other file, as its first line (after a first line <?xml, #! or @echo off) (# @SetVersion 1.0.3, <!-- @SetVersion 1.0.3 -->). A version line at the very start, right before such a first line, moves behind it. The dialog names the files that get a new line.
  • Files that no line names: AutoHotkey files get the new version, all others are left alone.

If no file gets the version (the project has no AutoHotkey files, or all are excluded), Set Version says why: the project has no settings.ahk-v2-plugin.ini (button Create Settings) or its [SetVersion] includes no file (button Edit Settings); both open the file at the section.

The head of compiler directives (Add Ahk2Exe compiler directives) takes over the line ;@SetVersion: it is removed, and its version becomes the default of the head.

The plugin then changes the lines in the editor (one Undo takes them all back), saves the files, commits and tags, and reports the result in a notification.

The line is read as Ahk2Exe reads it: ;@Ahk2Exe-SetVersion or ;@SetVersion in any case at the start of the line (spaces before it allowed), then the version; a comment after spaces (;@Ahk2Exe-SetVersion 1.0.2 ; comment) is not part of it. Lines in block comments /* */ and between ;@Ahk2Exe-IgnoreBegin and ;@Ahk2Exe-IgnoreEnd do not count. A script may have only one such line, with the version written out (a version computed with %...% cannot be changed). Ahk2Exe turns a text such as 1.0.2-dev into the binary version 1.0.2.0.

Code shared by several tools usually lies in a library folder outside the project; a deployed .exe contains the library as it was when it was compiled, a deployed .ahk uses the current library.

Libraries

Why library projects exist and how to work with them, step by step: Library projects. This section describes the rules.

A library is a file in the user library folder %A_MyDocuments%\AutoHotkey\Lib that scripts include with #Include <Name> (#Include <v2\Gui> loads Lib\v2\Gui.ahk). The plugin supports two ways to work with libraries:

  • Directly (the setting Library projects folder is empty): the files are edited in the library folder. File > New > AutoHotkey Library File creates one there; the name may contain folders (v2\Gui). A notification bar above such a file points to library projects, with the links Set Library Projects Folder... and Don't Show Again.
  • As library projects (the setting names a folder): one library = one project in that folder, with its own version, deployed into the library folder (Destination=%A_MyDocuments%\AutoHotkey\Lib\). The files in the library folder are copies; you change the project and deploy it.

Library projects

The names match: the project of Lib\v2\Gui.ahk is <Library projects folder>\Gui, with the source Gui.ahk. New projects lie directly in the library projects folder; the folders of the name (v2\) only become the target in the settings.ahk-v2-plugin.ini (Gui.ahk=v2\), while Destination is always the library folder itself. So one project can deploy several versions of a library, for example Lib\Gui.ahk and Lib\v2\Gui.ahk. You may still organize the projects in subfolders of the library projects folder; a folder with a settings.ahk-v2-plugin.ini is a project.

  • File > New > AutoHotkey Library Project... (also on the welcome screen) asks for the name (Json, v2\Gui) and creates the folder with the source (#Requires AutoHotkey v2.0 and ;@SetVersion 0.1.0) and a settings.ahk-v2-plugin.ini that deploys it into the library folder with Banner=@library (or Banner=find:banner.txt if the library projects folder or a folder above it contains a banner.txt) and a [SetVersion] that leaves out the AutoHotkey files in scratch\ and test\. The project opens in a window of its own. An existing folder is never touched.
  • Create Library Project 'Gui' in the context menu of a file of the library folder (here Lib\v2\Gui.ahk) that has no project yet, or the link of the same name in the notification bar "Library file without a library project." above that file, creates its project in the same way, with a copy of the file as source. The file in the library folder stays as it is and counts as a copy from then on; deploy the project to replace it.
  • Add to Library Project... (same places, and a second link in the notification bar) adds such a file to an existing library project instead: choose the project from the list (type to filter; projects in the same subfolder as the file come first). The file is copied into the project root, gets a line in [Install] that deploys it back to its place (Gui.ahk=v2\, relative to Destination), and the project opens. If the project already has a file of that name, the copy is called Gui_added.ahk and its line Gui_added.ahk={set target}: Deploy refuses it until you replace {set target} with the target. Rename the file later with Rename, and the line follows (see Renaming files of the project).
  • File > New > AutoHotkey Library File still works, but warns and offers to create a library project instead.
  • A copy in the library folder is read-only in the editor, and a notification bar says "Installed copy of library project 'Json' – edit the source and deploy" with the link Open Library Project.
  • Open Library Project 'Json' in the context menu of the editor and of the Project view (also below External Libraries > AutoHotkey Lib) opens the project in a window of its own, or brings its window to the front, and there the source at the line of the caret.
  • Ctrl+click on #Include <Json> still leads to the copy, because that is the file AutoHotkey loads; from there Open Library Project leads on to the source.

The plugin knows a copy by the copy lines of the projects: a file that a project deploys is its copy, also a second file of a project (JsonHelper.ahk in the project Json). If two projects deploy the same file, the one whose name matches wins. Libraries without a project are opened and edited as before. Use %LIBRARY_PROJECTS% in settings.ahk-v2-plugin.ini for files shared by all library projects; a banner shared by several projects is simpler with Banner=find:banner.txt.

A name whose first folder contains _ needs care: AutoHotkey may read #Include <a_b\c> as a.ahk if a_b\c.ahk is missing. To change the interface of a library without breaking the tools that use it, add the new function and mark the old one with @deprecated: its uses are struck out in every project that includes the library, and Code > Inspect Code lists them.
