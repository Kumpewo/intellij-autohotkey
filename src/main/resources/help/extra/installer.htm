Deploying tools and setting versions

Tools you use every day should not run from the project folder: every compilation there would replace the version you rely on. Two actions help:

  • Deploy to Local Target... copies a tool to a fixed place (for example C:\bin), optionally after compiling it.
  • Set Version... changes the version of the tool in its script, commits only this file and sets a Git tag.

The two are independent: you decide when a version is worth a number and when it is deployed. Both are in the Code menu and in the context menus of the editor and the Project view. Like Validate and Compile they apply to the script of the selected AutoHotkey run configuration if the current file is that script or included by it, otherwise to the current file. The folder of that script is the tool folder; the settings of both actions are in the file settings.ahk-plugin.ini there.

settings.ahk-plugin.ini

[Install]
Destination=C:\bin
Message=Close the running tool first.`nThen press Deploy.
RequiresAdmin=false
GenerateOverview=true
CompileBeforeInstall=true

[Overwrite]
mytool.exe=mytool.exe
pictures\*.png=pictures

[KeepExisting]
mytool.ini=%APPDATA%\mytool\

[Version]
TagPrefix=mytool

Create settings.ahk-plugin.ini (in the same menus) writes a documented default file into the tool folder: every option is explained in comments and commented out, so the defaults apply until you remove a ;. A commented-out switch shows the value that changes its default (usually true), so removing the ; is all it takes. Examples use the name of the script. If the file exists, the plugin asks before overwriting it. Deploy to Local Target... offers the same when the file is missing.

Comments are lines starting with ; (spaces before it are allowed); a ; later in a line is part of the value. Section and key names are case-insensitive. Values may be enclosed in double quotes, which are removed. Every key, and every source in a section, may appear only once. Unknown sections and keys are errors.

[Install]

KeyMeaning
DestinationAbsolute folder for relative targets, usable as %DESTINATION% (it wins over an environment variable of that name). May be omitted; then all targets must be absolute.
MessageText shown in the confirmation, for example "close the running tool first". `n is a line break; %DESTINATION% and environment variables are resolved, %% is a percent sign.
RequiresAdmintrue: all files are copied by one elevated process (one UAC prompt); the confirmation then always shows a prominent notice. The plugin does not find out by itself whether administrator rights are needed; without them copying into a protected folder fails with an error.
GenerateOverviewShow an overview in the confirmation (default true): the destination, "compile mytool.ahk" if compiling, and the lines of [Overwrite] and [KeepExisting] as written, without comments.
CompileBeforeInstallCompile the script first, like Compile with Ahk2Exe (the script needs ;@Ahk2Exe-Base). A compilation error stops the deployment before anything is copied.

Missing switches are false, except GenerateOverview.

[Overwrite] and [KeepExisting]

Each line is source=target. [Overwrite] replaces existing files; [KeepExisting] only copies if the target does not exist yet (for configuration files the user may have changed) and reports the others as skipped.

  • Source: a file relative to the tool folder, never outside of it (.. and absolute paths are not allowed). The wildcards * and ? are allowed in the file name, not in folder names; they are not recursive and match only files. A missing file or a wildcard without a match is an error, except for the executable that CompileBeforeInstall creates.
  • Target: absolute, or relative to Destination. Environment variables of the IDE (%APPDATA%) and %DESTINATION% are resolved. The target is a folder if it ends with \, /, . or .., if it is Destination itself (. or %DESTINATION%, also before it exists), or if it already exists as a folder; the file keeps its name. Otherwise it is the new file name. With a wildcard in the source the target is always a folder. Missing folders are created.
  • Several targets for one file: a source may appear only once per section; use wildcards to name it again: tool.exe=dest1, tool.ex?=dest2, tool.e?e=dest3.

[Version]

KeyMeaning
TagPrefixFirst part of the version tags <TagPrefix>/v<version>, e.g. mytool. Without it Set Version sets no tag. The folder name is not used, because it may contain characters that Git does not allow in tags, and after renaming the folder the plugin would no longer find the old tags.

Deploy to Local Target

Deploy to Local Target... needs settings.ahk-plugin.ini with at least one line in [Overwrite] or [KeepExisting]. The plugin then

  1. reads the file and checks everything: sources, targets, variables. Any problem is shown at once and nothing happens;
  2. always asks for confirmation (with the notice about administrator rights, the message, the overview and warnings; see below);
  3. compiles (if CompileBeforeInstall=true) and copies, in this order;
  4. shows a report in the Run tool window: what was compiled, copied and skipped. At the first failure the remaining steps are stopped; nothing is rolled back.

The confirmation warns if the script or another .ahk file of the tool folder is newer than the executable (with CompileBeforeInstall=false; the executable is the file named by ;@Ahk2Exe-ExeName, otherwise the script name with .exe), and if the tool folder has uncommitted changes. Deploying never commits or tags anything.

Copying writes the content into the target: a new file gets the permissions of its folder, an overwritten file keeps its own. The modification time of the source is kept. Environment variables are always resolved in the IDE, also with RequiresAdmin=true, so %APPDATA% is your folder even if the elevated process runs as another administrator.

There is no step to stop a running tool or to run a program before or after the deployment; use Message to remind yourself.

Uncommitted changes

The confirmation shows "The tool folder has uncommitted changes" when Git reports changes in the tool folder. The deployed version then does not match any commit: you cannot find out later which code it was built from, and a version tag points to a commit without these changes. Commit first (or use Set Version) if the deployed version should be reproducible.

Set Version

The version lives in the script, in the compiler directive that sets the file and product version of the executable:

;@Ahk2Exe-SetVersion 1.0.2

Set Version... reads this line and shows a dialog:

  • the next patch, minor or major version (1.0.2 becomes 1.0.3, 1.1.0 or 2.0.0; a text after the numbers such as -beta and a leading v are dropped), or any other version (without a leading v, which is unusual for Windows versions, and without spaces, commas, %, ; and `);
  • Commit the script: only this file is committed, other staged changes stay staged and other changed files stay as they are;
  • Create tag <TagPrefix>/v<version>: an annotated tag on the new commit (only together with the commit, so that the tag contains the new version). An existing tag is refused: choose another version;
  • the message of commit and tag, proposed as "Release mytool v1.0.3".

The plugin then changes the line in the editor (Undo takes it back), saves the file, commits and tags, and reports the result in a notification. Without Git, or if the tool folder is not in a repository, only the line is changed. Without settings.ahk-plugin.ini or without TagPrefix there is no tag. The dialog warns if the script has other uncommitted changes (they are committed together with the version) and if other files of the tool folder have changes (they are not committed).

The line is read as Ahk2Exe reads it: ;@Ahk2Exe-SetVersion in any case at the start of the line (spaces before it allowed), then the version; a comment after spaces (;@Ahk2Exe-SetVersion 1.0.2 ; comment) is not part of it. Lines in block comments /* */ and between ;@Ahk2Exe-IgnoreBegin and ;@Ahk2Exe-IgnoreEnd do not count. The script must have exactly one such line, with the version written out (a version computed with %...% cannot be changed). Ahk2Exe turns a text such as 1.0.2-dev into the binary version 1.0.2.0.

One repository can hold all your tools, one folder each, without branches per tool; the tag prefix tells the tools apart. Code shared by several tools usually lies in a library folder outside the repository; a deployed .exe contains the library as it was when it was compiled, a deployed .ahk uses the current library.
