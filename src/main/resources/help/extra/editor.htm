Editor: syntax, errors and colors

Syntax errors

The plugin parses AutoHotkey v2 while you type and marks syntax errors in the editor. Errors found by the grammar are shown as "Syntax error"; some rules have their own messages. AutoHotkey itself only checks a script when it loads it, so validating with AutoHotkey complements the plugin's checks.

Rules worth knowing:

  • The end of a line ends a statement. A statement continues on the next line only
    • after an operator at the end of the line (x := a +);
    • before a line that starts with and, or, is, in, contains, &&, ||, ??, ?, :, . (with a space after it) or ,;
    • inside parentheses ( ), also before a line that starts with any binary operator (+, *, =, <, |, := ...) or with the dot of a method call: 
      total := (price
        * quantity
        + shipping)
okButton := (win
        .AddButton("Default", "OK"))
    • in continuation sections (a string open at the end of a line, then ( ... )").
    Empty lines and comment lines between continued lines are allowed.
  • After the opening { of a block nothing may follow on the same line except a comment ("A line break must follow '{'"). One-line object literals like {x: 1} are fine.
  • Block comments /* ... */ are only recognized at the start of a line (also indented). Elsewhere they are an error, because AutoHotkey does not recognize them there.
  • else followed by a statement on the same line is accepted, but gets a warning, because it is hard to read.
  • global without a variable name is only allowed as the first statement of a function, method, hotkey or hotstring block; local and static always need a name.
  • A label Name: must stand alone on its line.
  • Before the first case of a switch only case or default may follow.
  • A keyword used as a name after the dot (obj.if) is an error.
  • An unknown directive (#Foo) gets a warning.

Lines the plugin marks.

if (x > 1) { y := 2        ; error: a line break must follow '{'
x := 1 /* note */          ; error: block comment not at the start of a line
else MsgBox "x"            ; warning: hard to read
DoWork() {
    x := 1
    global                 ; error: 'global' alone must be the first statement
}

Suppressing parser errors for one line

The parser does not know every construct. A known example is a call without parentheses whose first argument starts with (, such as SetTimer () => ..., 100. Put the pragma ;@ignore-next-line before such a line:

;@ignore-next-line the parser does not support this call form
SetTimer () => MsgBox("x"), 100

The parser errors of the next line are hidden and the line gets a marked background. Follow-up errors in later lines stay visible.

If validation shows that AutoHotkey accepts a file in which the plugin reports syntax errors, these errors are shown as "Syntax error (AutoHotkey accepts this code)".

Structure, breadcrumbs, sticky lines

  • The structure view (Alt+7, or Ctrl+F12 as a popup) lists hotkeys and hotstrings, classes with their methods and properties, functions and labels.
  • Breadcrumbs at the bottom of the editor and sticky lines at its top show the enclosing class, function, hotkey and control structures (if, loop, switch, case ...).

Highlighting occurrences

When the caret rests on a name, all occurrences of that name in the file are highlighted; Ctrl+Shift+F7 does the same on demand, F3/Shift+F3 move between them. As for navigation there is no type analysis: every name with the same spelling counts, ignoring case - variables, functions, classes, members after the dot and labels alike. Only for a local variable or parameter of a function just the occurrences of that variable count, and the local variables of functions are left out for any other name. Definitions and assignment targets (x := 1, obj.x += 1, parameters, declarations, for and catch ... as variables, function, class and property names, labels) are shown as write access, all other occurrences as read access. Names in strings and comments don't count.

Spell checking

The spell checker of the IDE (Settings > Editor > Inspections > Proofreading) checks comments, strings and the replacement text of hotstrings. Escape sequences (`n) are skipped; pragma and compiler directive comments (;@declare-type, ;@Ahk2Exe-...) and names in the code are not checked. Built-in names and their parts (MsgBox, LoopField), key names and terms like hotkey or hotstring are known words (dictionary AutoHotkey).

Code folding

The marks in the gutter (and Ctrl+NumPad -/+) fold these constructs if they span several lines:

  • everything between braces: classes, functions, methods, properties, control structures, hotkey and hotstring blocks, switch blocks, object literals (shown as {...});
  • block comments (/*...*/) and continuation sections ("(...)");
  • runs of two or more comment lines (shown as the first line) and of two or more #Include lines;
  • custom regions between ;region Name and ;endregion, or between ;{ Name and ;} (SciTE4AutoHotkey style), shown with their name.

Nothing is folded when a file is opened.

A custom region; folded it shows only Helpers.

;region Helpers
Twice(x) => x * 2
Half(x) => x / 2
;endregion

Typing aids

  • Brace matching highlights the matching ( ), [ ], { } and %...%. For % the 1st, 3rd ... percent sign in a line opens, the 2nd, 4th ... closes.
  • Typing " or ' inserts the closing quote; typing it again at the end steps over it. In code, an opening % brings its closing %.
  • Ctrl+/ comments or uncomments lines with ;, Ctrl+Shift+/ uses /* */.
  • Enter indents the new line according to the code style, also after case x:.
